# GitHub releases and updates

The three build commands embed a channel and version, package both executables, and publish complete GitHub releases. The desktop checks its installed channel, downloads on request, verifies the bundle, and installs after saving state and stopping the idle host.

The release commands require GitHub CLI signed in as the owner of `adamwawrzynkowski/kodem-ade` or a collaborator, because the **Release tags** ruleset lets only them create, move or delete `v*` and `nightly/v*` tags. A personal account's repository cannot make a collaborator an administrator, so every collaborator can publish releases. The repository is public, so the updater reads releases without authentication; it uses a GitHub CLI token when one is available. Tokens are read at request time and never embedded in a build.

Debug builds do not check for updates. Nightly checks only prereleases tagged `nightly/vX.X.X`; Production checks stable releases tagged `vX.X.X`. Versions compare numerically. Release commands select the workspace version or increment the latest channel's patch version, whichever is newer. `KODEM_VERSION=X.X.X` selects an explicit newer version. Releases contain `Kodem-macos-aarch64.zip`; GitHub's asset digest is required before an update is offered.

Downloaded bundles must match the channel, version, bundle identifier and repository. macOS code signatures are verified. The current build uses ad hoc signing, as before; Apple Developer ID signing and notarization are separate distribution requirements. SHA-256 authenticates the downloaded content against metadata retrieved from GitHub over HTTPS; an ad hoc signature does not establish publisher identity.

The app must be installed in a writable directory to replace itself. A download is staged on the same filesystem as the installed app. Finish active tasks and checks before applying the update; the host rejects shutdown while either is active. Applying an update closes host terminals. Drafts and settings are flushed before shutdown. The helper waits for the desktop to exit, replaces the app with rollback protection, and asks macOS to reopen it. Installation errors are retained in the staging directory's `install.log`.

## Windows and Linux packages

Recorded on 15 October 2026. Each platform builds natively: `scripts/build-macos.sh` on macOS, `scripts/build-linux.sh` on Linux, and `scripts/build-windows.sh` from Git Bash on Windows (`Build *.cmd` at the repository root). GPUI compiles its Direct3D shaders with the Windows SDK's `fxc.exe` in release builds, so Windows releases cannot be cross-compiled from macOS. One Windows build computer produces both processors: the build of the other processor is a cross-compilation with Visual Studio's C++ tools for it, and GPUI runs the SDK's `fxc.exe` for the build computer's processor. The second processor's archive joins the release that the first one published.

| Platform | Release asset | Package folder | Identity and metadata |
| --- | --- | --- | --- |
| macOS | `Kodem-macos-aarch64.zip`, installer `Kodem-macos-aarch64.dmg`, and their `.sha256` files | `Kodem.app`, `Kodem Nightly.app` | `Info.plist`, ad hoc code signature |
| Windows | `Kodem-windows-x86_64.zip`, `Kodem-windows-aarch64.zip`, installers `Kodem-windows-<processor>-setup.exe`, and their `.sha256` files | `Kodem`, `Kodem Nightly`, `Kodem Debug` | `release.json`, Authenticode signature, embedded icon and version resource |
| Linux | `Kodem-linux-x86_64.tar.gz`, installer `Kodem-linux-x86_64-setup.run`, their `.sha256` and optional `.asc` files | `kodem`, `kodem-nightly`, `kodem-debug` | `release.json`, optional detached OpenPGP signature |

`release.json` carries `name`, `identifier`, `version`, `channel`, `repository` and `build`. The Windows and Linux updaters require the installed folder's `release.json` to name the running channel, accept only archives whose entries are regular files and folders under the channel's package folder, then compare identifier, version, channel and repository. On Windows, when the running `kodem.exe` has a valid Authenticode signature, every new executable must carry a valid signature with the same certificate subject. The `kodem-update` helper installs the update; see [Installers and the update helper](#installers-and-the-update-helper).

A release build of a commit that already has a published release in its channel adds its archive to that release instead of allocating a new version. A draft release for the commit stops the build. An upload whose GitHub digest differs from the local archive is deleted from an existing release, or leaves a new release as a draft.

Windows executables are signed when a signing identity is configured and unsigned otherwise; `KODEM_REQUIRE_SIGNING=1` refuses unsigned release builds. Linux signing is optional unless `KODEM_REQUIRE_SIGNING=1`. License notices for Windows and Linux are generated at build time under `target/licensing/<target>/` with the macOS policy; the Linux graph needed reviewed clarifications for `harfrust`, `wayland-protocols-plasma`, `xim-ctext` and `xim-parser`. The Windows graph has no MPL dependency, so its package carries no `option-ext` source archive.

## One release for every platform

Recorded on 15 October 2026; revised the same day to build every platform in GitHub Actions. The **Release packages** workflow has five jobs. **Plan** runs `scripts/release.sh plan`, which uses `kodem_release_prepare` with the job's token to choose the version and the change list for the commit, and refuses a commit that already has a release. **macOS** (`xcode-27`, see below), **Windows** (`windows-2022`, x64 and Arm64) and **Linux** (`ubuntu-22.04`) build in parallel with `KODEM_RELEASE_VERSION`, `KODEM_RELEASE_COMMIT`, `KODEM_RELEASE_PREVIOUS` and `KODEM_RELEASE_NOTES` from Plan, so they package without publishing and install no Codex runtime. **Stage release**, the only job with `contents: write`, runs when every requested build succeeded: `kodem_release_verify_assets` requires each platform's archives with matching `.sha256` files, and `kodem_release_publish` with `KODEM_RELEASE_STAGE_ONLY=1` creates one draft, compares every upload with GitHub's SHA-256 digest, and leaves it a draft.

A draft has no tag. GitHub Actions cannot bypass rulesets in a personal account's repository, so the release becomes public when an owner account publishes the draft, which creates the tag: `scripts/release.sh nightly|production` does that with `kodem_release_finish` after following the run, requiring every asset to carry a SHA-256 digest; after **Run workflow** on GitHub, the run summary links the draft to publish. `kodem_release_dispatch` starts the workflow with a request identifier that the run name ends with, and `kodem_release_wait` prints each job's state, current step and finished steps whenever they change, and the elapsed time every five minutes. Runs of one channel are serialized, so two runs never choose the same version.

Recorded on 16 October 2026. Nightly showed the flat window controls of earlier macOS on macOS 27. Kodem uses the system's controls (GPUI only moves AppKit's `standardWindowButton`s); AppKit draws them in the style of the SDK that the executable links against. The `macos-14` runner linked against SDK 14.5 (`otool -l` showed `sdk 14.5` in `LC_BUILD_VERSION`; local builds on macOS 27 show `sdk 27.0`), so the macOS job now runs on `xcode-27` (Apple Silicon, macOS 27, Xcode 27) and refuses to build when `xcrun --show-sdk-version` is older than 27. The deployment target does not change: the executable still runs on macOS 14 and newer. The Clippy check stays on `macos-14` because it packages nothing.

## Installers and the update helper

Recorded on 16 October 2026. The user asked for installers in every Nightly and Production release (a disk image with an Applications link on macOS, a setup program that installs in the proper folder and adds a desktop shortcut on Windows), for no install scripts in the app folders, for in-app updates that install and reopen without an installer, and for a simpler and more reliable updater on Windows, possibly a separate process. Every release now carries an installer next to each update archive:

| Platform | Installer | What it does |
| --- | --- | --- |
| macOS | `Kodem-macos-aarch64.dmg` | `hdiutil` UDZO image with the app and a link to `/Applications`; `build-macos.sh` retries `hdiutil create` three times |
| Windows | `Kodem-windows-<processor>-setup.exe` | NSIS (`scripts/windows-installer.nsi`), for the current user without administrator rights: `%LOCALAPPDATA%\Programs\<app name>`, Start menu and desktop shortcuts that start in the user's folder, an entry under Installed apps with `Uninstall.exe`, `/S` for a silent installation. It waits until Kodem in the folder has quit (a running program cannot be opened for writing), replaces a folder that holds `release.json` as a whole, and refuses the Arm64 installer on x64 Windows |
| Linux | `Kodem-linux-x86_64-setup.run` | `scripts/linux-installer.sh` followed by the update archive; it installs in `~/.local/share/kodem/<package>` with a desktop entry and a command in `~/.local/bin`, and `--uninstall` removes them |

The package folders hold no scripts any more: `install.ps1`, `Install.cmd` and `install.sh` are gone, and the three updater scripts (`install-update.sh`, `install-update-windows.ps1`, `install-update-linux.sh`) are replaced by `crates/kodem-update`, a small program in every package (`Contents/MacOS/kodem-update`, `kodem-update.exe`, `kodem-update`). Updates still download the `.zip` or `.tar.gz` archive, so they never show an installer, and the archives keep their names and layout: an installed older version updates with its own script as before.

`updater::install` copies the downloaded version's helper into the stage folder and starts it there, outside the installed folder, with the installed folder, the new package and the stage as arguments. The desktop keeps the helper's standard input open; the end of that input, when the desktop exits, starts the installation, in place of a process ID that could be reused. The helper writes `ready` before the desktop quits and waits at most 120 seconds for it to exit. On Windows it then waits up to 15 seconds for `kodem.exe` and `kodem-host.exe` processes whose program lies in the installed folder, and ends the `kodem-host.exe` ones that remain: the desktop stopped the host, and the tool servers that providers start from `kodem-host.exe` hold no state. Every folder rename retries for up to 60 seconds on Windows, the move of the new package too, which an antivirus scan of the new files can hold; the PowerShell installer retried only the first move. A failed step moves the new folder to `failed`, puts the previous one back and opens it. macOS checks the code signature after the move. The new app starts outside its folder. On Windows the helper copies `Uninstall.exe` from the previous folder and writes the new version to the Installed apps entry when the installer made one. Windows keeps the running helper and `install.log` in the stage folder, so the helper marks it with `finished`, and `updater::remove_finished_updates`, which runs before each update check, removes such folders. A Windows signer is now compared by certificate subject, because a pinned thumbprint would refuse every update after the certificate is renewed.

`scripts/build-windows.sh` runs in three steps, `compile`, `package` and `finish`, all by default. In the release workflow they run separately: with the variable `SIGNPATH_ORGANIZATION_ID`, the job uploads the package folders, SignPath (`signpath/github-action-submit-signing-request` v3.0) signs `kodem.exe`, `kodem-host.exe` and `kodem-update.exe` with the artifact configuration `executables`, the job builds the archives and installers from the signed files, SignPath signs the installers with `installers`, and `finish` writes the checksums. `KODEM_SIGN_EXTERNALLY=1` makes each step check the signatures of the previous one with `signtool verify /pa`. Plan fails early when SignPath is half configured. Stage release downloads only the `package-*` artifacts, because the artifacts sent to SignPath hold unsigned copies. The artifact configurations are in `.signpath/artifact-configurations/` for reference; SignPath keeps its own copy. The repository allows only listed actions, and GitHub checks that list when it loads a workflow, even for steps that do not run: `scripts/configure-github.sh` allows `signpath/github-action-submit-signing-request@*`, and the workflow pins it to a full commit SHA. SignPath Foundation's free certificate requires an OSI-approved license, and `LICENSE` is proprietary.

Checked with a locked macOS `cargo build`, `cargo clippy --workspace --all-targets -D warnings` for macOS, Windows x64 and Linux (the cross checks used a scratch zig toolchain and a stand-in resource compiler and did not link), Clippy of `kodem-update` for Windows Arm64, `cargo fmt --check`, the license check after a refresh of the snapshot's input digests (no notice changed), `bash -n`, `sh -n`, a YAML parse of the release workflow and `xmllint` of the artifact configurations. Temporary checks, removed afterward: a copy of the helper with `open` replaced by `true` and a 3-second exit limit installed a new signed bundle after its input closed and removed the stage, left the app untouched when the parent did not exit, restored the previous bundle when the new one failed its signature check, refused an incomplete package before writing `ready`, and rejected wrong arguments; the `.run` installer installed, reinstalled and uninstalled a stand-in package in a scratch home and refused a truncated copy; `hdiutil` built and verified a disk image of a stand-in bundle with its Applications link; Homebrew's makensis 3.13 compiled the NSIS script for both processors without warnings (makensis on macOS needs a UTF-8 locale) and was uninstalled.

Not checked: the installers and an update cycle on Windows and Linux, the Windows process and registry calls of the helper at run time, a real release run of the workflow, and SignPath, which has no account here. App launch and control are excluded by the working agreement.

## Windows refused to start the update helper

Recorded on 16 October 2026. On Windows, applying an update failed with "The requested operation requires elevation. (os error 740)". Windows' installer detection treats a program whose name contains "update", "setup" or "install" as an installer that needs administrator rights unless its manifest declares a requested execution level, and `kodem-update.exe` had no manifest, so starting it failed. `crates/kodem-update/build.rs` now embeds `kodem-update.manifest` as resource 1 of type 24 (`RT_MANIFEST`) with `requestedExecutionLevel level="asInvoker"`, through `embed-resource` like the desktop's icon, and fails the build when the resource cannot be compiled.

The desktop also ran the helper of the installed version, so a broken helper could never be replaced by an in-app update. `updater::install` now copies the helper from the downloaded package, which the update has already verified (digest, identity, and the code signature on macOS or the Authenticode publisher on Windows). A fixed helper therefore installs its own release. The helper's contract stays fixed across versions: the installed folder, the new package and the stage as arguments, the end of standard input as the start signal, and `ready` in the stage. An installation that has the earlier helper still starts its own helper and fails with error 740, so it must be installed once with the setup program of the new release.

Checked with a locked macOS `cargo build`, `cargo clippy --workspace --all-targets -D warnings` and `cargo fmt --check`, and Clippy of `kodem-update` for Windows x64 with a stand-in resource compiler, which showed the generated resource script and the link of the compiled resource into the program. Not checked: the manifest in a real Windows build, and an update on Windows.

## Release highlights and the changelog gate

Recorded on 19 October 2026. The user asked for a What's new board that the app draws itself, so that no graphics are prepared before a release, with human titles that differ from the commit subjects, stored in the project; for every release to know which highlights its channel already shipped; for every release command to refuse to start until the highlights cover the changes, with a ready prompt for a model that writes them; and for the commits that only write the highlights to stay out of the commit list.

`changelog/highlights.toml` holds `[[headline]]` and `[[highlight]]` entries, newest first, and a `reviewed` commit. Its header documents the format and the visual kinds. `crates/kodem-desktop/build/highlights.rs` (from `build.rs`) parses it with `toml`, a build dependency only, checks it (unique ids written as `id = "…"` on their own line, text limits, counts of each visual, the dot-matrix characters of figures, icons that `src/icons.rs` embeds, a visual kind that differs from those of the three highlights above, a 40-character `reviewed` hash) and writes the chosen entries as Rust data for `release_notes.rs`. A mistake stops the build and names each problem.

| Step | What chooses the highlights |
| --- | --- |
| Release (`kodem_release_highlights`) | The ids in the file now, less the ids in the file at the channel's previous release tag, read with GitHub's contents API. A previous release without the file shows every entry; an unreadable one shows none. Nightly compares with the previous Nightly, Production with the previous Production, so Production shows everything the Nightlies added since its last release |
| Workflow | `release.sh plan` writes them as the `highlights` output; the macOS, Windows and Linux jobs pass it as `KODEM_RELEASE_HIGHLIGHTS` |
| Debug command (`kodem_release_local_highlights`) | The ids that the newest `nightly/v*` tag in the clone lacks, a preview of the next Nightly. A plain `cargo build` of Debug shows every entry; a release channel without the variable shows none |

`kodem_release_check_changelog` is the gate. It reads the non-merge commits from the channel's previous release tag to the release commit (GitHub's compare API) and the commits after the file's `reviewed` commit; `reviewed` must be an ancestor. A commit after it passes only when its subject starts with `Changelog:` and it changes only the highlights file; a `Changelog:` commit that changes more stops the release. Otherwise the gate lists the commits, prints a prompt that names them and the steps (read the header, `git show` each commit, write human highlights with true data, set `reviewed`, build, commit only the file as `Changelog: …`, do not push), copies it with `pbcopy` or `clip.exe` outside GitHub Actions, and fails. `release.sh nightly|production` runs it before it starts the workflow, the workflow's plan job runs it again (for **Run workflow** on GitHub), and `build-*.sh nightly|production` run it before they publish. Debug builds and the builds that only package for the workflow do not. Before a channel's first release there is nothing to check.

`kodem_release_changes` leaves the `Changelog:` subjects out of the commit list.

Checked with a read-only run of the functions against GitHub: the newest Nightly tag was `nightly/v0.1.52`, which predates the file, so all six ids were chosen; the gate passed for the committed file and, with a scratch copy whose `reviewed` was `bb131fb`, refused and listed `ef4e853`, `2e9c8fa` and `68bfc3b` with the prompt. The commit list filter was checked with `jq` on a sample. Shell syntax passed with macOS bash 3.2, which misparses apostrophes in a heredoc inside `$( )`, so the prompt is read with `read -d ''`. Not checked: a real workflow run with the new output.
