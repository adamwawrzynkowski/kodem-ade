# Provider integration

The host binds every conversation to a provider before starting its owner. Old task records and saved preferences default to Codex. A task can change its provider between turns, while no message is queued. The conversation of the earlier provider cannot move, so the task leaves it: the next message starts a conversation with the new provider and carries the earlier messages of the user and the replies as context. The transcript shows the change as a transfer row that names both agents. [Phase 7](progress.md) records the rules.

The providers are Codex, Claude Code, OpenCode, Antigravity and Grok. Antigravity replaced the "Google" placeholder on 21 October 2026, and Grok replaced the "xAI" placeholder on the same day. Antigravity and Grok support is in beta, and the desktop marks it so. The Devin integration was removed on 12 October 2026; the store moves its old tasks aside when it opens.

## Caller and ownership

The desktop sends `ConnectRuntime { provider }` to inspect an integration and `SetAgentPreferences` to persist choices before a task exists. `CreateTask` stores the complete selection; subsequent model and permission edits apply to that task. Runtime catalogs and saved model choices are keyed by `Provider`; sign-in state and usage are keyed by provider account.

`kodem-host/src/provider.rs` routes operations and owns submission acceptance, the task owner and attachment validation. `kodem-host/src/orchestrator.rs` owns the lifecycle of a task's main turn: queue claims, delivery proof, the start and the end of a turn, the wait for subagents, and the publication of the outcome. `providers/codex.rs` implements app-server operations. `providers/claude.rs`, `claude_transport.rs` and `claude_transcript.rs` implement Claude Code's stream-json control protocol. `kodem-core/src/providers/codex.rs` contains the low-level Codex CLI transport and its wire permission mappings.

The design compared a universal typed session-event interface with native provider drivers. The native drivers were selected because the protocols differ in when a turn is acknowledged: Codex answers `turn/start` before the turn completes, while Claude Code echoes the message identity in its event stream. A universal interface would require migrating the existing event decoder without removing those lifecycle differences. Shared queue claiming, uncertainty handling and review capture were retained from the other candidate to keep delivery rules consistent.

That decision stands. The orchestrator is not a session-event interface: each driver keeps its own session loop, dispatch and protocol, and there is no driver trait. A driver only reports a lifecycle fact as an `orchestrator::Signal` at the moment its own protocol proves it. Codex reports `Delivered` when `turn/start` or `turn/steer` answers, which can be after `turn/started` and even after `turn/completed`. The decision therefore accepts these signals in any order: `Delivered` marks the turn as running only while the task is still `Starting`, and never changes a later state.

## Subagents on another provider

Each provider session of a task receives one more MCP server, `kodem`: Claude Code through `--mcp-config` and the allow rule `mcp__kodem`, Codex through `-c mcp_servers.kodem.*` for that process only. The server is the host executable itself, started as `kodem-host mcp --root <data dir> --task <task>` (`kodem-host/src/mcp.rs`). It keeps no state and turns each tool call into one request on the host's socket. Its tools are `list_agents`, `delegate_task`, `task_status` and `task_cancel`.

`delegate_task` starts an ordinary task (`kodem-host/src/delegation.rs`) whose `Lineage` names the parent. A model is found by identity or name without regard to case, spaces and punctuation, and it decides the provider. A task that only reads uses the checkout of its parent while the parent works, with `AccessMode::ReadOnly` for Codex and the tools that a review blocks for Claude Code; `Task::shares_checkout` exempts it from the rule of one writer for each checkout. A task that may write gets a worktree and branch of its own that start with the parent's present files. The parent's agent reads the result with a tool call that waits at most 45 seconds, below the shortest default limit of a provider, and calls again for a longer task. Both conversations show a "Delegated task" transfer row, and the parent shows "Subagent result" when the result is first read. A delegated task gets no `kodem` server, so it cannot delegate further. Stop on the parent also stops its delegated tasks that work.

## Lifecycle decisions

The model follows T3 Code's Orchestrator V2 without its event log: the task and message rows stay the stored truth.

| Part | Where | Rule |
| --- | --- | --- |
| Input | `Signal` (from a driver), `Command` (from the host) | A signal is an observation. `Command::Claim` asks for the next message; `Command::Finalize` publishes an outcome. |
| Facts | `Facts`, read under the host lock | The queue, an unconfirmed delivery, a busy checkout, and options the provider does not support. Only a claim reads the queue. |
| Decision | `decide(&Task, &Facts, &Input)` | No I/O. Returns events, effects, and a refusal that is reported after the events are stored. |
| State change | `apply(&mut Task, &Event)` | The only code that changes a task for these events. |
| Storage | `Store::commit` | One transaction for the task, the ledger changes and the released final answer. Before, a completed turn was several separate writes. |
| Effects | `Effect::Send`, `Effect::Capture` | A message to send returns to the session loop that owns the transport. The checkout capture runs after the commit, without the host lock, and ends in `Command::Finalize`. |

Each counted turn is a `Run`: `apply_run` creates it when a message is claimed, lets a steering message join it, and ends it with the published outcome. [Phase 3](progress.md) records its rules.

Three rules of the model are now in one place. Only the main turn completes a task. The end of a turn is held (`OutcomeHeld`) until no subagent works (`OutcomeReleased`). The end of the provider turn and the publication of the outcome (`Finalized`, after the checkout capture) are two steps.

The inputs of all tasks are decided one at a time, because `orchestrate` takes the locked host. The user is alerted when a step changes the state of the task, as `save_task_with_notification` did.

Claude Code reports the same signals at its own moments. The CLI has no acknowledgement of a turn start, so a message written to it is `TurnStarted`, and the echo of the message identity is `Delivered`, which then only settles the delivery. A model request that nobody submitted is `TurnStarted` too: the CLI continues by itself. The driver keeps its wait for such a continuation (`Held.ready`): until that wait ends, it does not report `TurnEnded`. A message that cannot be built for the CLI is `DeliveryFailed` without uncertainty.

Not on this path, and still written by the drivers: the states of subagents, the `Waiting` state of an input request, the outcome change on Stop while an outcome is held, compaction, context usage, drafts, titles and settlement.

## Task kinds and session rules

A task has a kind: `Coding`, `Chat` or `Review` (`TaskKind`). Old task records have no kind and read as `Coding`. The kind decides the working directory, the standing instructions and the tool rules of the provider session. `provider::instructions` returns the instructions, and both drivers give them when a provider process starts, so they also hold after a resume.

Every kind ends its instructions with the plan rules of its provider (`CLAUDE_PLAN_RULES` or `CODEX_PLAN_RULES`): a plan before work of more than one step, one step in progress at a time, each step completed as soon as it is done, the plan changed when the work changes. They name the provider's own tool: `TaskCreate` and `TaskUpdate` (or `TodoWrite`) for Claude Code, and `update_plan` for Codex. The Claude Code rules are stricter, because the CLI defers its task tools and their own description keeps them for complex work: they name the `ToolSearch` query that loads them, require a plan for every request of two or more steps, and give the order of calls (in progress, the work, completed). Neither CLI offers that tool to Kodem by default. Claude Code 2.1.296 offers its task tools to models after the 4.x family only when the launch names one of them in `--allowedTools` or `--tools`, so every session allows `PLAN_TOOLS` (`TodoWrite`, `TaskCreate`, `TaskUpdate`, `TaskList` and `TaskGet`); with Opus 5.5 it then offers the four `Task` tools, which load through `ToolSearch`. Codex 0.162.1 offers `update_plan` only with `tools.update_plan.enabled`, which `thread/start` and `thread/resume` set in `config`. Codex refuses `update_plan` in Plan mode, so the rules tell it to propose the plan there. The plan of the main conversation becomes `Task.plan`. Claude Code reports it as those tool calls; a subagent's `TodoWrite` is its own and is ignored. Codex reports the whole plan in `turn/plan/updated`, and only the main thread's report counts. The start of a turn clears a plan whose steps are all done, because it belongs to the turn before.

| Kind | Working directory | Claude Code | Codex |
| --- | --- | --- | --- |
| `Coding` | The project checkout or a task worktree | `--append-system-prompt` with the plan rules only; `--allowedTools` with the plan tools | `developerInstructions` with the plan rules only; `config.tools.update_plan.enabled` |
| `Chat` | `chats/<task>` in the data directory, empty, one per chat | `--append-system-prompt`; `--allowedTools WebSearch WebFetch` | `developerInstructions`; `config.web_search = "live"` |
| `Review` | `reviews/<task>`: a detached worktree at the reviewed commit | `--append-system-prompt`; the permission mode of the task; `--disallowedTools` with `Edit`, `Write`, `NotebookEdit` and the Bash rules for `git push`, `git commit` and the `gh` commands that write | `developerInstructions`; the access of the task |

A review has the same approval rule as a coding task: `TaskEdit::Access` and `TaskEdit::ProviderAccess` apply to it, and the provider session uses the rule of the task. The desktop never starts a review in a plan mode. Only the denied tools of Claude Code are fixed for a review; Codex has no such list, so its sandbox enforces a review only with `AccessMode::ReadOnly`. Options of a chat or a review do not become the options of new tasks: only a `Coding` task saves them with `Store::save_task_preferences`.

The approval rule is remembered for each model in `Settings.access_choices`, keyed by `AutoCompact::model_key`. Only an explicit choice records it: `SetAccessChoice` for a draft or for Settings, and an access edit of a task of any kind. A plan mode is not recorded. The desktop applies the recorded rule to the options of a new task (`Shell::with_access`), after the project default and the last used options, and when a draft changes its model.

`CreateReview` resolves its target in `kodem-core/src/git/review.rs`. A pull request is fetched from the remote whose address ends with the owner and repository of the pull request's URL, into `refs/kodem/reviews/<task>/head` and `/base`; the references are deleted once the worktree exists, because the detached worktree keeps the commits reachable. A branch is resolved from local references without a fetch. The merge base of the head and the base branch becomes `Task.baseline`, so `Comparison::Baseline` captures the reviewed changes with the existing capture code. The fetch can update the remote-tracking reference of the base branch, as any `git fetch` does. `DeleteTask` removes a review's worktree with `git worktree remove --force` and a chat's folder, and only at the path the host derives from the task's identity.

Only a `Coding` task follows the branch of its checkout and takes part in merge-based settlement. A task on a branch of its own settles when that branch is merged into the default branch. A task on the default branch settles once every file that its turns left changed (`checkpoint::turn_changes`) is committed after its baseline and no file that they touched has uncommitted changes; that observation holds until its next turn. A chat has no checkout, so `complete_turn` captures no diff for it.

`CreateTask` takes an optional `base` commit for a new worktree. The desktop uses it for the task that fixes a review's findings: its branch starts at the reviewed commit.

## Capabilities and persistence

Settings stores both the last selected provider and each provider's last model, reasoning and access. Delayed window-layout saves preserve these host-owned preferences. The model picker, composer and sidebar use the same provider identity and logo. Model changes clear old context occupancy.

Codex reasoning levels and image modalities come from `model/list`. Claude Code models, reasoning levels and native slash commands come from its control handshake. Fast mode is a capability of a model (`Model.fast`) and a choice of a task and of the preferences (`fast`), changed with `TaskEdit::Fast`. Claude Code marks a model with `supportsFastMode`, and the driver sets the `fastMode` flag setting through `apply_flag_settings` before a turn; print mode serves fast mode only through that flag. Codex lists a `Fast` entry in a model's `serviceTiers` (`priority`, with a description such as "2x speed, increased usage"; older runtimes list `fast` in `additionalSpeedTiers`), and `turn/start` sends that tier as `serviceTier`, or `null` to return to standard speed. OpenCode lists the fast mode of a model as a model of its own, `<model>-fast`, built from models.dev `experimental.modes`; the catalog folds it into the model it speeds up and a fast turn runs it. The usage panel also shows session cost when a provider supplies an amount and currency. Unsupported choices are rejected at host boundaries as well as disabled in the desktop. The app's `/provider` and `/model` actions open local pickers.

Each provider owns its CLI authentication. Settings supplies its sign-in and sign-out commands for Terminal. Credentials are neither copied into workspace settings nor shared across providers.

## Models and defaults

`RuntimeInfo.models` holds concrete models only, and no name contains "default" or "recommended": `provider::model_name` removes such markers. Claude Code lists its own choice as a stand-in entry with the identity `default`. The driver drops it when another entry resolves to the same model, which is the case for Opus 5.5 (`opus`). When no other entry selects that model, the stand-in is kept under the resolved model identity and the name from its description. Codex lists concrete models only.

`RuntimeInfo.default_model` is always one of the listed models: for Claude Code the entry whose identity and name contain "opus" and "5.5", for Codex the one that contains "6.1" and "sol". When the CLI does not list that model, the CLI's own default is used, then the first entry. A task or preference without a model runs as `default_model`: `provider::effective_model` resolves it and both drivers pass it explicitly (`--model` and `set_model`, or the `model` field of `thread/start`, `thread/resume` and `turn/start`). Reasoning chosen without a model is validated against the default model. A Codex owner that starts before any catalog was read reads `model/list` first.

The host stores the last model per account and per project in `Settings.model_choices` whenever preferences are saved or a task is created or edited. At start the host clears the retired Claude Code identity `default` from tasks and saved choices (`Store::retire_model`), so they fall back to the default model.

## One-shot generations

The Git workspace's AI actions (commit title and description, change and commit explanations, code review, pull request review) run as one-shot generations, not as tasks. `Request::Generate` starts one under an identity that the desktop chooses, and `Request::GenerationStatus` reads its progress in waits of up to 30 seconds, so a long review outlives no connection's read timeout. The host forgets a generation after a status reports it done, or 10 minutes after it ended unread. `provider::generate` resolves the account and calls the provider's `generate`; each one keeps no conversation and gives the model no tools, with a 10-minute limit:

- Codex: an ephemeral, read-only thread with every feature and MCP server off (`Codex::start_restricted`, shared with title generation), the request's schema as `outputSchema`, and `summary: "auto"` so that reasoning text streams.
- Claude Code: `-p` with `--no-session-persistence`, `--tools ""`, no setting sources and `--json-schema` for a structured answer, run in the repository, so its CLAUDE.md is read.
- OpenCode: a session with one deny-all permission rule and the instructions as its `kodem` entry, deleted after the answer together with the server.
- Antigravity: runs in a session folder of its own, not the repository, with a pre-tool hook (`antigravity-hook --generation`) that denies every call without asking the host. The conversation is deleted by identity afterwards (`antigravity::delete_conversation`); its summary in `jetbox_summaries_proto.pb` stays.
- Grok: a session in `default` mode whose permission requests are all rejected once (never "always", which the CLI saves per project), deleted with `_x.ai/session/delete` and swept by identity. Grok runs its built-in read-only tools without asking, so those can still run.

Providers without native structured output receive the schema in the instructions (`provider::generation_instructions`).

## Compaction

`Request::CompactTask` compacts the conversation of a task that has a provider session and no running turn. The request is refused while a turn runs ("Compact after this turn finishes"), while delivery is uncertain, and before the first message ("There is nothing to compact yet. Send a message first."). It is not queued behind a running turn, because a control message is not durable. The reply is `Ok` as soon as the compaction started; its result arrives with the task. `ComposerCommand::Compact` is in a provider's composer catalog only for a task that has a session.

`provider::begin_compaction` records the task's state in host memory and sets the task to `Running`. Queued input therefore waits, and no edit or second compaction starts. Input sent in steer mode during a compaction starts the next turn instead of joining one. `provider::end_compaction` returns the task to its earlier state without a completion alert, review capture or change of `updated`. A failed or stopped compaction leaves the notice "Context was not compacted: ..." and never fails the task or its queued input. A lost provider connection during a compaction restores the earlier state and is not an uncertain delivery, because no user input was in flight. If the host stops during a compaction, the task is recovered as any task that was working.

Claude Code: the owner sends `/compact` as a user message with its own UUID. The CLI reports `status: "compacting"`, a `compact_boundary` and a result without a model reply. The transcript writes "Context compacted from X to Y tokens.", and the owner then reads `get_context_usage`, because the boundary counts the summary alone. Codex: the owner calls `thread/compact/start`. Codex runs a turn that holds one `contextCompaction` item and reports the smaller context in `thread/tokenUsage/updated` while that item is open, which is when the driver writes the same notice. Both show `ActivityKind::Compacting`, and Stop interrupts a compaction like a turn.

Automatic compaction follows `Settings.auto_compact.rule(provider, model)`, where the model is the one that runs the task. Two mechanisms apply it.

1. The provider's own limit, which also works in the middle of a long turn. Claude Code starts with `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=<threshold>`, or with `DISABLE_AUTO_COMPACT=1` when the rule is off. Codex receives `model_auto_compact_token_limit` in the thread configuration: the threshold share of the model's context window as Codex reports it, or a limit no context reaches when the rule is off. The window of a model is known after any task of that model reported usage; until then Codex keeps its own limit.
2. A check between turns in the owner (`provider::begin_due_compaction`). When input is queued for the next turn and the last usage reading is at or above the threshold, the owner compacts first and then starts the turn. The check runs before the turn and not after the previous one, so a task that is never continued spends nothing. A reading is acted on once, and the reading a compaction leaves behind does not start another one.

Both limits are fixed when a provider process opens the conversation. Before each turn the owner compares the current rule with the one in effect and, when they differ, starts a new process that resumes the same conversation. A changed rule, model override or threshold therefore applies no later than the next turn. A queued message is claimed only after this step and after a compaction, so a compaction never resends or drops a prompt.

## Accounts

A provider can have several signed-in accounts at once. Each added account owns one CLI configuration directory under `<data dir>/accounts/<provider>/<id>` (mode 0700), passed through `CLAUDE_CONFIG_DIR` or `CODEX_HOME` whenever Kodem starts that CLI. The default account has no directory: the variable is removed, so the CLI uses its standard location and existing sign-ins work without setup.

`kodem-host/src/accounts.rs` owns the registry (`Settings.accounts`), live `AccountStatus` values kept in host memory, sign-in, sign-out, removal and the background refresh that runs with the workspace poll. `Account::apply` in `kodem-core/src/providers/account.rs` is the only place that binds a process to an account; every provider CLI start uses it. For Claude Code it also removes `CLAUDE_CODE_EFFORT_LEVEL` for every account, because a task chooses its own effort, and `CLAUDE_SECURESTORAGE_CONFIG_DIR` for added accounts, because they must not share one credential store. It never removes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or any other variable that selects an authentication method; see "Provider terms". When such a variable is set, the CLI uses it for every account, and the account status shows the CLI's `authMethod` in place of a plan.

Kodem never reads, copies or links credentials. Sign-in writes a small `.command` script that runs the provider's own login command in Terminal and then polls the CLI's status; `RefreshAccount` ends that wait. A new account directory receives symbolic links to non-secret configuration of the standard directory only: for Claude Code `settings.json`, `CLAUDE.md`, `skills`, `commands`, `agents`, `plugins`, `output-styles`, `keybindings.json` and `projects`; for Codex `config.toml`, `AGENTS.md`, `prompts`, `skills`, `rules` and `sessions`. Identity and token files (`.claude.json`, `.credentials.json`, `auth.json`) are never linked. MCP servers that Claude Code stores in `.claude.json` are therefore not shared with added accounts.

A task records its account. Changing it is allowed between turns, except that a started task whose account is at a usage limit keeps that account until the limit resets (`accounts::limit_reached`; the desktop disables the choice and the host refuses the edit). A Claude Code task keeps its conversation: the session owner stops its process and resumes the same session under the new account before the next turn, which works because `projects` is shared. A Codex task can change account only before its thread exists, because Codex keeps paginated thread history in per-home SQLite state. Removing an account signs it out, deletes its directory and returns saved choices for new tasks to the default account. Tasks that used it keep their reference and are blocked until another account is chosen; a removed identity is never replaced silently.

The background refresh reads accounts that are in use on every pass: the account of the next new task and the account of every task that is working or changed in the last 15 minutes. Any other account is read at most once per 30 minutes, or on request.

Usage belongs to an account, not to a provider. Codex quotas come from `account/rateLimits/read` and its rolling notifications. Claude Code quotas come from the `get_usage` control request and `rate_limit_event`. Both are stored in `AccountStatus.usage`. `get_usage` also reports usage credits as `rate_limits.extra_usage`: the spend and the cap in cents, the use in percent and the currency. They are stored in `UsageLimits.spend` when `is_enabled` is true. A Claude Enterprise seat has no five-hour or weekly window, so its credits are the limit that the sidebar and the composer show, and a spend at or above the cap counts as a reached limit. An account with plan windows shows its credits in the usage details only. The report does not carry the reset time of the credits.

## Claude Code

`providers/claude.rs` drives `claude -p` with stream-json input and output and `--permission-prompt-tool stdio`. `claude_transport.rs` owns the process and control requests; `claude_transcript.rs` maps events to transcript items. One process per task owner holds the conversation. A new task starts with a host-chosen `--session-id`; `provider_thread` is saved when the CLI first acknowledges input, and later processes use `--resume`. Model, effort and permission mode follow the task between turns through `set_model`, `apply_flag_settings` and `set_permission_mode`. Changing the account, clearing the effort, changing the automatic compaction rule, changing `Settings.claude_artifacts`, or entering or leaving `bypassPermissions` starts a new process with `--resume`.

Print mode sets the entry point `sdk-cli`, and the CLI keeps Artifacts off for that entry point. `Settings.claude_artifacts` starts each process with `CLAUDE_CODE_ARTIFACT=1`, which turns them on. The setting is off by default. The probes that read the composer catalog start with the same variable, so the catalog of a new task lists the same commands as its session. Artifacts also need a first-party claude.ai sign-in whose plan and organization policy allow them; the CLI decides that, and Kodem does not check it.

Every submission carries a UUID derived from its identity. The CLI echoes it in `command_lifecycle`, replayed user messages and the turn result, which confirms delivery. A message for a running turn is sent with `priority: "next"` and joins that turn. Reconciliation after a lost connection looks for the same UUID in the CLI's stored session transcript, restores the stored items and settles the turn. That transcript format is internal to the CLI, so anything unreadable leaves delivery unknown.

Text and thinking stream as they arrive. Each tool call becomes one `Tool` message with a `ToolCall`; edits carry a diff built from the CLI's structured patch. `TodoWrite`, `TaskCreate` and `TaskUpdate` update `Task.plan` instead of the transcript. Subagents use the existing subagent model: a link message in the parent, a child transcript, and completion of the task held until background agents finish. The CLI may continue by itself after a background agent reports; the driver treats that as a follow-up turn of the same task. Tool approvals, `AskUserQuestion` and `ExitPlanMode` arrive as `can_use_tool` and use the shared request flow (`claude/requestApproval`, `claude/requestUserInput`, `claude/plan/requestApproval`). "Allow for this session" returns the CLI's suggestions scoped to the session, so nothing is written to the checkout's settings.

Titles use one tool-less Haiku call under the task's account with `--no-session-persistence` and no settings, and fall back to the first prompt line.

## Antigravity (beta)

`providers/antigravity.rs` drives the Antigravity CLI (`agy`) in its headless stream-json mode: `agy --input-format stream-json --output-format stream-json -p=`, one prompt per input line and one `result` event per turn. `antigravity_transcript.rs` maps the stream's `step_update` events and the conversation's stored `transcript_full.jsonl` to transcript items, and `antigravity_import.rs` reads stored conversations. `kodem-core/src/providers/antigravity.rs` finds the CLI (`~/.local/bin/agy`, `%LOCALAPPDATA%\agy\bin` on Windows) and reads the CLI's conversation index, `~/.gemini/antigravity-cli/conversation_summaries.db`, read-only.

One process per task owner holds the conversation. The CLI has no control messages in this mode, so the model, the reasoning level, plan mode and Kodem's additions are fixed when a process starts; a change starts a new process that continues the conversation with `--conversation <id>`. Stop sends SIGINT, which the CLI reports as an interrupted turn before it ends. The next turn starts a new process.

The CLI asks nobody in headless mode: a tool that needs approval is refused. Kodem therefore adds a session folder to the workspaces with `--add-dir`, and the CLI reads `.agents/hooks.json`, `.agents/mcp_config.json` and `.agents/rules/*.md` of every workspace:

- `hooks.json` runs `kodem-host antigravity-hook --root <data dir> --task <task>` before every tool call (`PreToolUse`, matcher `*`, timeout six hours). The hook sends the call to the host (`Request::AntigravityHook`). The session owner answers at once (`auto_approve`, `deny` with a reason, or `allow`, which leaves the call to the CLI's own rules), or with a ticket while the user decides; the hook asks again with the ticket every 400 ms. The CLI runs the hook through a shell, so its words are quoted.
- `mcp_config.json` adds the `kodem` MCP server. A delegated task gets none.
- `rules/kodem.md` is an `always_on` rule with the standing instructions of the task's kind and the plan rules.

The CLI orders the workspaces of a conversation by path and starts a subagent in the first one, so the session folder must sort after the task's folder. It is `<temp>/kodem-antigravity/<task>` when that path sorts after the task's folder, which it does on macOS (`/var/folders/...`) and Linux (`/tmp`), else `<data dir>/kodem-antigravity/<task>`. The owner deletes the folder when it ends. The system can clear old files of its temporary folder, so a turn starts a new process when the folder's `hooks.json` is missing.

## Grok (beta)

`providers/grok.rs` drives xAI's Grok Build CLI (`grok`) in its agent mode, `grok agent --no-leader stdio`: the Agent Client Protocol (ACP) as JSON-RPC lines, with xAI's extension methods whose names start with `_x.ai/`. `grok_transcript.rs` maps the session updates, live and stored, to transcript items, and `grok_import.rs` reads stored sessions. `kodem-core/src/providers/grok.rs` finds the CLI (`~/.grok/bin/grok`, which the installers also link from `~/.local/bin`, then the usual program folders) and reads the CLI's sessions: `sessions/<encoded folder>/<session>/summary.json` and `updates.jsonl` in the CLI's home, `~/.grok` or `GROK_HOME`. In the product, Grok is the provider, Grok Build is the CLI, and xAI is the company.

One process per task owner holds the conversation, an ACP session. `session/new` gives the session the `kodem` MCP server and the standing instructions of the task's kind with the plan rules (`_meta.rules`); the CLI stores them in the session's system prompt, which is also how a stored session is known as Kodem's. Later processes continue it with `session/load`, which replays the history before it answers; the replay is not written again. The model, the reasoning level (`session/set_config_option`), plan mode (`session/set_mode`) and "Always approve" (`_x.ai/yolo_mode_changed`) follow the task between turns. A change of the account or of the automatic compaction rule starts a new process that loads the same session. Every process starts with `GROK_DISABLE_AUTOUPDATER=1`.
