# Provider integration

The host binds every conversation to a provider before starting its owner. Old task records and saved preferences default to Codex. A provider cannot change after session startup or while retained outgoing input exists. Starting another conversation preserves the original provider history.

The providers are Codex and Claude Code. The Devin integration was removed on 12 October 2026; the store moves its old tasks aside when it opens.

## Caller and ownership

The desktop sends `ConnectRuntime { provider }` to inspect an integration and `SetAgentPreferences` to persist choices before a task exists. `CreateTask` stores the complete selection; subsequent model and permission edits apply to that task. Runtime catalogs and saved model choices are keyed by `Provider`; sign-in state and usage are keyed by provider account.

`kodem-host/src/provider.rs` routes operations and owns submission acceptance, the task owner, queue claims, attachment validation and terminal-turn persistence. `providers/codex.rs` implements app-server operations. `providers/claude.rs`, `claude_transport.rs` and `claude_transcript.rs` implement Claude Code's stream-json control protocol. `kodem-core/src/providers/codex.rs` contains the low-level Codex CLI transport and its wire permission mappings.

The design compared a universal typed session-event interface with native provider drivers. The native drivers were selected because the protocols differ in when a turn is acknowledged: Codex answers `turn/start` before the turn completes, while Claude Code echoes the message identity in its event stream. A universal interface would require migrating the existing event decoder without removing those lifecycle differences. Shared queue claiming, uncertainty handling and review capture were retained from the other candidate to keep delivery rules consistent.

## Task kinds and session rules

A task has a kind: `Coding`, `Chat` or `Review` (`TaskKind`). Old task records have no kind and read as `Coding`. The kind decides the working directory, the standing instructions and the tool rules of the provider session. `provider::instructions` returns the instructions, and both drivers give them when a provider process starts, so they also hold after a resume.

| Kind | Working directory | Claude Code | Codex |
| --- | --- | --- | --- |
| `Coding` | The project checkout or a task worktree | No added instructions or tool rules | No added instructions |
| `Chat` | `chats/<task>` in the data directory, empty, one per chat | `--append-system-prompt`; `--allowedTools WebSearch WebFetch` | `developerInstructions`; `config.web_search = "live"` |
| `Review` | `reviews/<task>`: a detached worktree at the reviewed commit | `--append-system-prompt`; the permission mode of the task; `--disallowedTools` with `Edit`, `Write`, `NotebookEdit` and the Bash rules for `git push`, `git commit` and the `gh` commands that write | `developerInstructions`; the access of the task |

A review has the same approval rule as a coding task: `TaskEdit::Access` and `TaskEdit::ProviderAccess` apply to it, and the provider session uses the rule of the task. The desktop never starts a review in a plan mode. Only the denied tools of Claude Code are fixed for a review; Codex has no such list, so its sandbox enforces a review only with `AccessMode::ReadOnly`. Options of a chat or a review do not become the options of new tasks: only a `Coding` task saves them with `Store::save_task_preferences`.

The approval rule is remembered for each model in `Settings.access_choices`, keyed by `AutoCompact::model_key`. Only an explicit choice records it: `SetAccessChoice` for a draft or for Settings, and an access edit of a task of any kind. A plan mode is not recorded. The desktop applies the recorded rule to the options of a new task (`Shell::with_access`), after the project default and the last used options, and when a draft changes its model.

`CreateReview` resolves its target in `kodem-core/src/git/review.rs`. A pull request is fetched from the remote whose address ends with the owner and repository of the pull request's URL, into `refs/kodem/reviews/<task>/head` and `/base`; the references are deleted once the worktree exists, because the detached worktree keeps the commits reachable. A branch is resolved from local references without a fetch. The merge base of the head and the base branch becomes `Task.baseline`, so `Comparison::Baseline` captures the reviewed changes with the existing capture code. The fetch can update the remote-tracking reference of the base branch, as any `git fetch` does. `DeleteTask` removes a review's worktree with `git worktree remove --force` and a chat's folder, and only at the path the host derives from the task's identity.

Only a `Coding` task follows the branch of its checkout and takes part in merge-based settlement. A chat has no checkout, so `complete_turn` captures no diff for it.

`CreateTask` takes an optional `base` commit for a new worktree. The desktop uses it for the task that fixes a review's findings: its branch starts at the reviewed commit.

## Capabilities and persistence

Settings stores both the last selected provider and each provider's last model, reasoning and access. Delayed window-layout saves preserve these host-owned preferences. The model picker, composer and sidebar use the same provider identity and logo. Model changes clear old context occupancy.

Codex reasoning levels and image modalities come from `model/list`. Claude Code models, reasoning levels and native slash commands come from its control handshake. The usage panel also shows session cost when a provider supplies an amount and currency. Unsupported choices are rejected at host boundaries as well as disabled in the desktop. The app's `/provider` and `/model` actions open local pickers.

Each provider owns its CLI authentication. Settings supplies its sign-in and sign-out commands for Terminal. Credentials are neither copied into workspace settings nor shared across providers.

## Models and defaults

`RuntimeInfo.models` holds concrete models only, and no name contains "default" or "recommended": `provider::model_name` removes such markers. Claude Code lists its own choice as a stand-in entry with the identity `default`. The driver drops it when another entry resolves to the same model, which is the case for Opus 5.5 (`opus`). When no other entry selects that model, the stand-in is kept under the resolved model identity and the name from its description. Codex lists concrete models only.

`RuntimeInfo.default_model` is always one of the listed models: for Claude Code the entry whose identity and name contain "opus" and "5.5", for Codex the one that contains "6.1" and "sol". When the CLI does not list that model, the CLI's own default is used, then the first entry. A task or preference without a model runs as `default_model`: `provider::effective_model` resolves it and both drivers pass it explicitly (`--model` and `set_model`, or the `model` field of `thread/start`, `thread/resume` and `turn/start`). Reasoning chosen without a model is validated against the default model. A Codex owner that starts before any catalog was read reads `model/list` first.

The host stores the last model per account and per project in `Settings.model_choices` whenever preferences are saved or a task is created or edited. At start the host clears the retired Claude Code identity `default` from tasks and saved choices (`Store::retire_model`), so they fall back to the default model.

## Compaction

`Request::CompactTask` compacts the conversation of a task that has a provider session and no running turn. The request is refused while a turn runs ("Compact after this turn finishes"), while delivery is uncertain, and before the first message ("There is nothing to compact yet. Send a message first."). It is not queued behind a running turn, because a control message is not durable. The reply is `Ok` as soon as the compaction started; its result arrives with the task. `ComposerCommand::Compact` is in a provider's composer catalog only for a task that has a session.

`provider::begin_compaction` records the task's state in host memory and sets the task to `Running`. Queued input therefore waits, and no edit or second compaction starts. Input sent in steer mode during a compaction starts the next turn instead of joining one. `provider::end_compaction` returns the task to its earlier state without a completion alert, review capture or change of `updated`. A failed or stopped compaction leaves the notice "Context was not compacted: ..." and never fails the task or its queued input. A lost provider connection during a compaction restores the earlier state and is not an uncertain delivery, because no user input was in flight. If the host stops during a compaction, the task is recovered as any task that was working.

Claude Code: the owner sends `/compact` as a user message with its own UUID. The CLI reports `status: "compacting"`, a `compact_boundary` and a result without a model reply. The transcript writes "Context compacted from X to Y tokens.", and the owner then reads `get_context_usage`, because the boundary counts the summary alone. Codex: the owner calls `thread/compact/start`. Codex runs a turn that holds one `contextCompaction` item and reports the smaller context in `thread/tokenUsage/updated` while that item is open, which is when the driver writes the same notice. Both show `ActivityKind::Compacting`, and Stop interrupts a compaction like a turn.

Automatic compaction follows `Settings.auto_compact.rule(provider, model)`, where the model is the one that runs the task. Two mechanisms apply it.

1. The provider's own limit, which also works in the middle of a long turn. Claude Code starts with `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=<threshold>`, or with `DISABLE_AUTO_COMPACT=1` when the rule is off. Codex receives `model_auto_compact_token_limit` in the thread configuration: the threshold share of the model's context window as Codex reports it, or a limit no context reaches when the rule is off. The window of a model is known after any task of that model reported usage; until then Codex keeps its own limit.
2. A check between turns in the owner (`provider::begin_due_compaction`). When input is queued for the next turn and the last usage reading is at or above the threshold, the owner compacts first and then starts the turn. The check runs before the turn and not after the previous one, so a task that is never continued spends nothing. A reading is acted on once, and the reading a compaction leaves behind does not start another one.

Both limits are fixed when a provider process opens the conversation. Before each turn the owner compares the current rule with the one in effect and, when they differ, starts a new process that resumes the same conversation. A changed rule, model override or threshold therefore applies no later than the next turn. A queued message is claimed only after this step and after a compaction, so a compaction never resends or drops a prompt.

## Accounts

A provider can have several signed-in accounts at once. Each added account owns one CLI configuration directory under `<data dir>/accounts/<provider>/<id>` (mode 0700), passed through `CLAUDE_CONFIG_DIR` or `CODEX_HOME` whenever Kodem starts that CLI. The default account has no directory: the variable is removed, so the CLI uses its standard location and existing sign-ins work without setup.

`kodem-host/src/accounts.rs` owns the registry (`Settings.accounts`), live `AccountStatus` values kept in host memory, sign-in, sign-out, removal and the background refresh that runs with the workspace poll. `Account::apply` in `kodem-core/src/providers/account.rs` is the only place that binds a process to an account; every provider CLI start uses it. For Claude Code it also removes `CLAUDE_CODE_EFFORT_LEVEL` for every account, because a task chooses its own effort, and `CLAUDE_SECURESTORAGE_CONFIG_DIR` for added accounts, because they must not share one credential store. It never removes `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or any other variable that selects an authentication method; see "Provider terms". When such a variable is set, the CLI uses it for every account, and the account status shows the CLI's `authMethod` in place of a plan.

Kodem never reads, copies or links credentials. Sign-in writes a small `.command` script that runs the provider's own login command in Terminal and then polls the CLI's status; `RefreshAccount` ends that wait. A new account directory receives symbolic links to non-secret configuration of the standard directory only: for Claude Code `settings.json`, `CLAUDE.md`, `skills`, `commands`, `agents`, `plugins`, `output-styles`, `keybindings.json` and `projects`; for Codex `config.toml`, `AGENTS.md`, `prompts`, `skills`, `rules` and `sessions`. Identity and token files (`.claude.json`, `.credentials.json`, `auth.json`) are never linked. MCP servers that Claude Code stores in `.claude.json` are therefore not shared with added accounts.

A task records its account. Changing it is allowed between turns, except that a started task whose account is at a usage limit keeps that account until the limit resets (`accounts::limit_reached`; the desktop disables the choice and the host refuses the edit). A Claude Code task keeps its conversation: the session owner stops its process and resumes the same session under the new account before the next turn, which works because `projects` is shared. A Codex task can change account only before its thread exists, because Codex keeps paginated thread history in per-home SQLite state. Removing an account signs it out, deletes its directory and returns saved choices for new tasks to the default account. Tasks that used it keep their reference and are blocked until another account is chosen; a removed identity is never replaced silently.

The background refresh reads accounts that are in use on every pass: the account of the next new task and the account of every task that is working or changed in the last 15 minutes. Any other account is read at most once per 30 minutes, or on request.

Usage belongs to an account, not to a provider. Codex quotas come from `account/rateLimits/read` and its rolling notifications. Claude Code quotas come from the `get_usage` control request and `rate_limit_event`. Both are stored in `AccountStatus.usage`. `get_usage` also reports usage credits as `rate_limits.extra_usage`: the spend and the cap in cents, the use in percent and the currency. They are stored in `UsageLimits.spend` when `is_enabled` is true. A Claude Enterprise seat has no five-hour or weekly window, so its credits are the limit that the sidebar and the composer show, and a spend at or above the cap counts as a reached limit. An account with plan windows shows its credits in the usage details only. The report does not carry the reset time of the credits.

## Claude Code

`providers/claude.rs` drives `claude -p` with stream-json input and output and `--permission-prompt-tool stdio`. `claude_transport.rs` owns the process and control requests; `claude_transcript.rs` maps events to transcript items. One process per task owner holds the conversation. A new task starts with a host-chosen `--session-id`; `provider_thread` is saved when the CLI first acknowledges input, and later processes use `--resume`. Model, effort and permission mode follow the task between turns through `set_model`, `apply_flag_settings` and `set_permission_mode`. Changing the account, clearing the effort, changing the automatic compaction rule, or entering or leaving `bypassPermissions` starts a new process with `--resume`.

Every submission carries a UUID derived from its identity. The CLI echoes it in `command_lifecycle`, replayed user messages and the turn result, which confirms delivery. A message for a running turn is sent with `priority: "next"` and joins that turn. Reconciliation after a lost connection looks for the same UUID in the CLI's stored session transcript, restores the stored items and settles the turn. That transcript format is internal to the CLI, so anything unreadable leaves delivery unknown.

Text and thinking stream as they arrive. Each tool call becomes one `Tool` message with a `ToolCall`; edits carry a diff built from the CLI's structured patch. `TodoWrite`, `TaskCreate` and `TaskUpdate` update `Task.plan` instead of the transcript. Subagents use the existing subagent model: a link message in the parent, a child transcript, and completion of the task held until background agents finish. The CLI may continue by itself after a background agent reports; the driver treats that as a follow-up turn of the same task. Tool approvals, `AskUserQuestion` and `ExitPlanMode` arrive as `can_use_tool` and use the shared request flow (`claude/requestApproval`, `claude/requestUserInput`, `claude/plan/requestApproval`). "Allow for this session" returns the CLI's suggestions scoped to the session, so nothing is written to the checkout's settings.

Titles use one tool-less Haiku call under the task's account with `--no-session-persistence` and no settings, and fall back to the first prompt line.

## Claude Code and account evidence

Checked on 11 and 12 October 2026 against Claude Code 2.1.296 and Codex 0.162.1.

Without a model call: the control handshake and its catalog; `get_usage`, `apply_flag_settings`, `set_model`, `set_permission_mode`, `mcp_status`, `stop_task` and `interrupt` before any turn; `bypassPermissions` is refused unless the process was launched with it; `--session-id`, `--replay-user-messages`, `--forward-subagent-text` and `--thinking-display summarized` are accepted; `claude auth status` reports signed out for a fresh configuration directory while the default stays signed in; the Keychain service name is derived from the configuration directory for reads and deletes alike; `--resume` loads a session from another configuration directory when `projects` is linked and fails with "No conversation found" when it is not; removing an added account, including its sign-out, leaves the default sign-in intact; a Codex home that shares only `sessions` sees none of the turns of a paginated thread, while one that also shares the SQLite home sees them.

With eight short Haiku turns in scratch directories: thinking deltas, image input, the echoed message UUID, steering with `priority: "next"`, interruption, compaction, the edit patch shape, session-scoped permission suggestions, `AskUserQuestion`, `ExitPlanMode` approval and refusal, a background subagent with its lifecycle events and a permission request of its own, and one complete turn through the host including an approval and a generated title. Scratch directories and their session transcripts were removed.

Not covered: a turn under a second signed-in account, so the API accepting a session produced under another account is an assumption; the todo and task-list tools, which this CLI version did not offer, so their mapping follows the documented shapes only; `api_retry`, a reached usage limit, synchronous subagents and nested subagents; opening Terminal for sign-in; in-app Codex sign-in through `account/login/start`. `ToolStatus` has no interrupted value, so a tool cut off by Stop ends as failed.

Checked on 12 October 2026 against Claude Code 2.1.296 and Codex 0.162.1.

With short turns on the cheapest models (Haiku 5.5 and GPT-6-Luna) in scratch directories: `/compact` on an idle Claude Code session and its events; `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` starting a compaction before the next request once the context is above that share; `thread/compact/start` and its events, including that Codex also accepts it for an empty thread and refuses `turn/start` while it runs; `model_auto_compact_token_limit` honoured from `thread/start` and from `thread/resume` in a new process. A turn with the default models (Opus 5.5, GPT-6.1-Sol) was not run.
