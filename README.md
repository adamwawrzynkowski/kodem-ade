# Kodem ADE

A native Rust and GPUI coding workspace. Task conversations, Git review, captured feedback and a terminal run through a durable local host. Providers are Claude Code through its stream-json control protocol and Codex through its app-server CLI. You can stay signed in to several accounts of one provider and choose the account per task. The Codex integration requires CLI 0.153.4 or newer.

## Build on macOS

Requires Apple Silicon and macOS 14 or newer. Double-click one of these files in Finder:

| Command | Result |
| --- | --- |
| [Build Debug.command](Build%20Debug.command) | Builds `target/debug/Kodem Debug.app`, local only |
| [Build Release Nightly.command](Build%20Release%20Nightly.command) | Builds `target/nightly/Kodem Nightly.app` and publishes a GitHub prerelease |
| [Build Release Production.command](Build%20Release%20Production.command) | Builds `target/production/Kodem.app` and publishes the latest stable GitHub release |

All commands check Apple Command Line Tools, Git, Rust 1.97.1, rustfmt, Clippy and a complete Codex runtime package at or above the minimum version. They reuse the newest valid installed Codex package, or install the minimum version when none is available. They install missing prerequisites, fetch locked Cargo dependencies, format-check, compile, package and verify signatures. They do not launch or stop the app. Debug keeps its current local workflow. Debug builds compile dependencies with optimization, so the debug app stays responsive; Kodem's own crates stay unoptimized with Debug assertions. The first debug build after a dependency change takes several minutes longer. Release commands keep local bundles and publish a ZIP for installation and updates; they do not replace an app in `/Applications` during publication.

Release commands require GitHub CLI with repository write access, a clean checkout, and a commit already available on GitHub. They never commit or push source. Run `gh auth login` before publishing. Each channel starts at the workspace version and increments its patch version on subsequent releases. Set `KODEM_VERSION=X.X.X` to choose a newer version explicitly. Nightly uses `nightly/vX.X.X` tags and GitHub prereleases; Production uses `vX.X.X` and marks the release as latest. Uploads remain drafts until GitHub's SHA-256 digest matches the archive.

**One release for every platform.** On macOS, `Build Release Nightly.command` and `Build Release Production.command` publish macOS, Windows (x64 and Arm64) and Linux together. After choosing the version, the command starts the **Release packages** workflow (`.github/workflows/release.yml`) for that commit, builds macOS meanwhile, waits for the workflow, downloads its archives, checks their `.sha256` files, and publishes one release with all of them. Nothing is published if any platform fails, and a failed macOS build cancels the workflow. The workflow runs `scripts/build-windows.sh` on `windows-2022` and `scripts/build-linux.sh` on `ubuntu-22.04`; it builds and uploads workflow artifacts only. It must be on the default branch on GitHub, and `gh` needs the `workflow` scope (`gh auth refresh -s workflow`). `KODEM_RELEASE_PLATFORMS` limits the workflow to `windows` or `linux`; an empty value publishes macOS only. Windows signing in the workflow uses the repository secrets `KODEM_SIGN_PFX_BASE64` and `KODEM_SIGN_PFX_PASSWORD`, or the variable `KODEM_ALLOW_UNSIGNED=1`; the Linux signature uses the secrets `KODEM_GPG_PRIVATE_KEY` and `KODEM_GPG_PASSPHRASE` with the variable `KODEM_GPG_KEY`. Actions minutes of a private repository count against the account's quota, and Windows minutes count double. The Windows and Linux release commands still publish their own platform, or add it to the release of the same commit.

```sh
./'Build Debug.command'
./'Build Release Nightly.command'
./'Build Release Production.command'
```

Set `KODEM_NONINTERACTIVE=1` to skip the final Return prompt. Incremental builds reuse `target/aarch64-apple-darwin/`. Build metadata is embedded in the executable and `Contents/Info.plist`; `Contents/Resources/BuildInfo.txt` includes the build ID. Logs are saved under `target/build-debug.log`, `target/build-nightly.log` and `target/build-production.log`. Bundles use ad hoc signatures; Developer ID signing and notarization are not configured.

## Build on Windows

Builds for x64 and Arm64 Windows 10 version 1809 or newer (and Windows 11 on Arm). Requires [Git for Windows](https://git-scm.com/download/win), Python 3, and Visual Studio 2022 Build Tools with the **Desktop development with C++** workload, the C++ build tools of each processor you build for (**MSVC x64/x86** and **MSVC ARM64**), and a Windows 11 SDK. Release builds compile GPUI's shaders with the SDK's `fxc.exe`. Nightly and Production build both processors by default, cross-compiling the one that the build computer does not have; Debug builds the computer's own. `KODEM_WINDOWS_ARCH` chooses `x86_64`, `aarch64` or both, for example `KODEM_WINDOWS_ARCH=aarch64`. Double-click `Build Debug.cmd`, `Build Release Nightly.cmd` or `Build Release Production.cmd`, or run `scripts/build-windows.sh debug|nightly|production` from Git Bash. The commands install rustup, the pinned toolchain and the Windows Codex package when missing, and write `target/<channel>/windows-<processor>/<app name>/` with `kodem.exe`, `kodem-host.exe`, `release.json`, notices and `Install.cmd`. `Install.cmd` copies the package to `%LOCALAPPDATA%\Programs\<app name>` and adds a Start menu shortcut. Release commands publish `Kodem-windows-x86_64.zip` and `Kodem-windows-aarch64.zip` to one release, each with its `.sha256` file. Each installed app updates from the archive of its own processor.

Release executables must carry an Authenticode signature, so SmartScreen and Smart App Control accept them. Configure one identity: `KODEM_SIGN_TRUSTED_SIGNING_METADATA` and `KODEM_SIGN_TRUSTED_SIGNING_DLIB` for Azure Trusted Signing, `KODEM_SIGN_CERT_SHA1` for a certificate in the Windows certificate store or on a hardware token, or `KODEM_SIGN_PFX` with `KODEM_SIGN_PFX_PASSWORD`. Signatures are timestamped (`KODEM_SIGN_TIMESTAMP_URL` overrides the server) and verified with `signtool verify /pa`. Nightly and Production refuse to publish unsigned executables unless `KODEM_ALLOW_UNSIGNED=1`; Debug signs only when an identity is configured. The executables embed the app icon and version information.

## Build on Linux

Requires x86_64 Linux. Run `./'Build Debug.command'`, `./'Build Release Nightly.command'` or `./'Build Release Production.command'` (they run `scripts/build-linux.sh` on Linux). The command checks a C compiler, `pkg-config`, Python 3 and the development files of xkbcommon, xkbcommon-x11, fontconfig, freetype and xcb, prints the packages to install for Debian/Ubuntu, Fedora and Arch when one is missing, and installs rustup, the pinned toolchain and the Linux Codex package. It writes `target/<channel>/kodem[-nightly|-debug]/`; run its `install.sh` to install it under `~/.local/share/kodem/`, add a desktop entry and a command in `~/.local/bin`. Release commands publish `Kodem-linux-x86_64.tar.gz` and its `.sha256` file.

The package needs the glibc of the build system or newer; the build prints that version and records it in `BuildInfo.txt`, so build on the oldest distribution you support, for example Ubuntu 22.04 or Debian 12. At runtime Kodem needs libxkbcommon, libxkbcommon-x11, fontconfig, freetype and Vulkan or OpenGL drivers, on Wayland or X11. Linux runs unsigned programs; set `KODEM_GPG_KEY` to publish a detached OpenPGP signature (`.asc`) next to the archive, and `KODEM_REQUIRE_SIGNING=1` to refuse publishing without one.

A commit that is already released on one platform keeps its version: building the same commit on another platform adds that platform's archive to the existing release.

## Updates

Install the released app in a writable folder: Applications on macOS, `Install.cmd` on Windows, `install.sh` on Linux. Nightly and Production check their own GitHub release channels at startup and every 30 minutes. Debug does not make update requests. The titlebar shows `Kodem X.X.X` or `Kodem Nightly X.X.X`, with the version in a subtle rounded badge.

After an update, the first launch of the new version shows **What's new** once: the subjects of the commits since the previous release of the same channel, newest first, without merges (at most 100). A new installation and Debug builds show none, and the command palette's **What's new** opens it again. The release commands read the list from GitHub when they choose the version and embed it in the app; the Windows and Linux builds in GitHub Actions receive the same list. The desktop records the shown version in `release-notes.json` in the data directory.

When an update is available, **Update ↓** appears beside Settings. Click it to download and view progress. Once the archive's size, SHA-256 digest, bundle identity, channel, version and code signature have been checked, the control becomes a reload icon. On Windows, an app signed with a trusted certificate accepts only updates from the same certificate; Linux packages rely on the GitHub digest. Click to save state, stop the idle host, install and reopen. Active tasks and checks block restart; terminal sessions close when the update is applied. Failed downloads can be retried. Installation failures restore the previous bundle and retain a log.

The repository and its releases are public, so updates need no GitHub account. When GitHub CLI is signed in, the updater uses its token for a higher API rate limit; credentials are never bundled. Only the owner's accounts can publish: a ruleset reserves the release tags for them (see [Security](SECURITY.md)). The Codex runtime remains a separate prerequisite installed by the build commands. See [release implementation](docs/implementation/releases.md) for the channel and installation contract.

## Start a task

Open the app, choose a repository, then create a task. Tasks use the current checkout by default. Choose **Settings → Workspace → Default task location** to default to a new worktree instead; a repository needs an initial commit for that option. Each new task starts with the saved preference, and you can override it in the composer for that task. Selecting a task never checks out another branch in your original working directory.

The setup dialog (it opens on first launch, and later from the command palette) lists Claude Code, Codex, Git, Git LFS and GitHub CLI with what Kodem found. **Install** opens a terminal window that runs the official installer, so password prompts and progress stay visible; choose **Check again** when it finishes. Claude Code comes from `claude.ai/install.sh` (`install.ps1` on Windows). Codex comes as the complete Codex package from its latest GitHub release, unpacked into Kodem's runtimes folder. Git comes from Apple's Command Line Tools on macOS, from winget on Windows and from the distribution's package manager (apt, dnf, pacman, zypper or apk) on Linux. Git LFS and GitHub CLI come from Homebrew on macOS, winget on Windows and the package manager on Linux. The GitHub CLI installer then runs `gh auth login` if no account is signed in. The scripts are kept in the data directory's `installers/` folder.

Each provider uses its own CLI authentication. Kodem never reads or stores credentials. If you are already signed in to a provider's CLI, its default account works with no setup. To sign in from Kodem, open **Settings → Accounts**, choose the provider and select **Sign in**. Terminal opens the provider's own sign-in command (`claude auth login` or `codex login`).

If Codex is installed only by Kodem's build setup, its executable is `~/.local/share/kodem/runtimes/0.153.4/bin/codex`. For Claude Code, install the [official CLI](https://code.claude.com/docs/en/overview).

### Workspaces

A narrow rail on the left edge of the window swaps the window between three workspaces. Each workspace lists only its own threads, and keeps the thread that was open in it and the unsent draft of its start screen. Option-Command-1, Option-Command-2 and Option-Command-3 open them; the command palette and the View menu list them too. A marker on a rail icon shows that a thread of that workspace waits for you, works, or has an unread result. A thread always opens in its own workspace, also from the command palette and from **Next task that needs you**. While the sidebar is closed, the rail also holds the new-thread, search, palette, repository and settings buttons.

| Workspace | What it is for |
| --- | --- |
| **Agentic Coding** | Tasks in a project checkout or worktree. This is the workspace described in the rest of this document. |
| **Chat** | Conversations without a project: questions, web search and ordinary talk with a model. |
| **Review** | A local, read-only review of a pull request or a branch of a project. |

**Chat.** A chat has no project, branch, changes panel, file browser or terminal. The host gives each chat an empty scratch folder of its own under `chats/` in Kodem's data directory and deletes it with the chat. Choose the model, effort and approvals in the composer as usual. Claude Code may search the web and read pages in a chat without asking; Codex runs a chat with live web search. A session instruction tells the model that there is no repository and that it should name its sources.

**Review.** Choose the project in the heading, then pick a pull request or switch to **Branches** and pick a branch. Pull requests come from GitHub CLI (`gh pr list`), so they need `gh` installed and signed in; branches need only Git. The default branch is not listed, because branches are compared with it. A remote-tracking branch is not listed when a local branch of the same name is at the same commit. Text in the composer is optional and goes to the reviewer as focus notes. **Start review** does this, all on this machine:

- For a pull request, the host fetches its head and its base branch from the Git remote that points to the pull request's repository. For a branch, it reads what the local repository already has and fetches nothing.
- It checks out the reviewed commit in a detached worktree under `reviews/` in Kodem's data directory. Your checkout, your branches and your index are not touched. Uncommitted changes of your checkout are not part of a review; the picker says so when you pick the checked-out branch.
- The review runs as a thread in that worktree. Its changes panel opens on **Reviewed changes**: the diff between the merge base and the reviewed commit. You can select lines there and ask the reviewer about them.

A review is told to change and publish nothing. A session instruction forbids edits, commits, pushes and pull-request comments. Claude Code also runs a review without its file-editing tools, and with `git push`, `git commit` and the `gh` commands that write to GitHub denied. Everything else follows the approval rule, which you choose in the composer of a review as in Agentic Coding: the rule decides which other commands run without a question. Codex runs a review in the sandbox of the access you choose, so only **Read only** enforces the instruction in its sandbox. The composer of a review shows **READ ONLY** beside the approval menu and has no Build or Plan mode, and the host refuses to stage a file in a review. Kodem itself never pushes, comments or changes a pull request.

When a review has reported, a **Findings** bar appears under the title. **Fix in Agentic Coding** creates a task in the same project, in a new worktree whose branch starts at the reviewed commit, sends it the reviewer's findings, and opens it in Agentic Coding where it starts working. It uses the options that new tasks of that project start with. The task is told to check each finding before it changes anything and to leave the result as local changes. Deleting a review removes its detached worktree; the project, its branches and the pull request stay as they are.

### Accounts

**Settings → Accounts** lists every account of each provider with its email, plan, sign-in state and limit windows. **Add account** creates a separate configuration directory for the provider's CLI under Kodem's data directory and opens the CLI's sign-in for it. Kodem starts the CLI with that directory (`CLAUDE_CONFIG_DIR` or `CODEX_HOME`), so each account keeps its own sign-in and you do not sign in again to switch. Settings, instructions, skills and saved sessions are linked from the CLI's standard directory, so an added account behaves like your normal setup. MCP servers that Claude Code stores in `~/.claude.json` are not shared, because that file also holds the account identity. Moving Kodem's data directory signs added Claude Code accounts out, because the macOS Keychain entry is keyed to the directory path.

Choose the account in the composer: the model chip shows the account, and its menu lists the provider's accounts above the models, each with its plan and fullest limit. A task keeps its account. You can move a Claude Code task to another account between turns, and it resumes the same session. A Codex task keeps its account after its first turn, because Codex stores thread history per configuration directory; start a new task to use another Codex account. When a task's account is signed out, a notice above the composer offers to sign in. When it reaches its limit, the notice shows when the limit resets. Kodem does not suggest another account then, and a started task stays on its account until the reset; see [Provider terms](#provider-terms). Removing an account signs it out and deletes its directory; tasks that used it wait until you choose another account.

The same menu has **Make default for _project_**. It saves the current provider, account, model, reasoning effort and access as the starting point of new tasks in that project. **Settings → Projects** shows each project's default and clears it. A project without a default follows the last options you chose.

### Composer

The model picker has a provider rail and lists only concrete models; there is no "default" entry. A new task starts with Opus 5.5 on Claude Code and GPT-6.1 Sol on Codex until you choose another model. Kodem remembers the model you chose last for each account, and for each account in each project, and starts the next task there with it. A project default set from the picker comes first. A conversation stays bound to its provider after startup; start a new conversation to use another provider. Choose the model and account, reasoning effort and access from their separate composer chips, or with Shift-Command-M, Shift-Command-E and Shift-Command-A. The effort slider supports dragging and arrow keys. The context and usage meters sit in a small tab on the composer's top edge. Its toolbar holds attachments and skills, then the model and its effort on the left, and the mode, the approvals and the send button on the right. The model chip shows the provider's logo, the account's color square and the model; the account's name is in its tooltip and in the menu. Stop and send stay on the right. Claude Code has two separate choices: the mode, Build or Plan, and the approval rule that says what the agent may do without asking. Shift-Tab switches between Build and Plan; the approval rule you chose returns when a task leaves plan mode. Kodem remembers the approval rule you chose last for each model. A new task with that model starts with it in every workspace and project, before the project default. For Codex, Shift-Tab steps through the access modes that still ask; modes that remove approval need an explicit choice. Codex access defaults to Workspace; AI auto-approve routes permission requests to its risk-based AI reviewer while retaining the workspace sandbox. Claude Code uses the permission modes that its session advertises. Unsupported reasoning, image input, steering and account quota actions are unavailable rather than mapped to another provider's behavior. These controls apply to the next turn and cannot change during active execution.

Compose a prompt and press Return; Shift-Return inserts a newline. Type `/` for the provider's commands and skills, and `@` to mention a file of the task's checkout. Commands and file changes stream into the transcript. Permission requests, plan reviews and questions appear inside the composer with the provider's own decisions; a decline can carry a note that tells the agent what to do instead. Answer every question and select **Send answers**; each new request triggers the configured attention notification. Async questions remain available after the model finishes or the app restarts; answers reach the active turn immediately or start the next turn. While a turn runs, an empty draft turns the send button into Stop, and a draft sends with the configured delivery (Queue or Steer); Command-Return sends it the other way. A transport failure with uncertain delivery requires explicit history reconciliation; Kodem does not silently resend your prompt.

The sidebar leads with what needs you. **Needs you** holds tasks that wait for input or approval, or that failed. **Working** holds running tasks. **Ready for review** holds finished results that you have not opened yet. The remaining tasks follow. Completed tasks of all projects collect in one Settled list at the bottom of the sidebar, above the account, and a project that has only settled tasks has no group in the feed. Rows show task status and elapsed time, the provider logo, a colored dot for a non-default account, and the task branch. Threads receive a short model-generated title in the background. Manual renames take precedence. Filter by project or search titles, projects and branches. A task's +/− badge opens its saved completion snapshot; later checkout edits do not change it. Older tasks show no historical total until another turn completes. The footer shows the composer account's limit windows.

Command-K opens the command palette: one ranked list of every action, thread and account, across all workspaces. Control-Tab and Control-Shift-Tab move to the next and previous task, Command-1 to Command-9 open a task by its position in the feed, and Option-Command-A opens the next task that needs you. **Settings → Shortcuts** lists all keys.

### Provider terms

Kodem runs the providers' own CLIs. Your use of them is under your own agreement with Anthropic or OpenAI, and breaking those terms can get an account suspended. Kodem is built to stay inside them, as read on 11 October 2026:

- **Sign-in.** Sign-in happens in the provider's own CLI and browser flow. Kodem never reads, stores or passes on credentials or tokens, and it does not send requests to a provider itself.
- **Unmodified CLI.** Kodem starts the installed `claude` and `codex` programs as published. It does not remove an authentication method: if `ANTHROPIC_API_KEY` is set in Kodem's environment, Claude Code uses it and the account shows that method instead of a plan.
- **Your own accounts only.** Add only accounts that are yours, for example a personal and a work account. Do not share an account, and do not use another account to continue after a usage limit. Both providers forbid getting around their limits. Kodem therefore does not offer another account when a limit is reached, and it keeps a started conversation on its account until the limit resets.
- **Ordinary use.** Plan limits assume ordinary use by one person. Kodem reads the quotas of accounts that tasks use; an idle account is checked at most every 30 minutes, or when you ask.
- **Work and personal data.** Added Claude Code accounts share the session history of the default account. Do not continue a work conversation under a personal account, or the reverse, if your employer's policy forbids it.

Kodem is not affiliated with, endorsed by or partnered with Anthropic or OpenAI. Claude Code and Codex are named to say what Kodem runs, and their providers' logos mark their models; neither use is licensed by its owner. If you distribute a build that runs Claude Code to other people, Anthropic's [terms for products that run Claude Code](https://code.claude.com/docs/en/legal-and-compliance) apply to you as the distributor. The sources and the remaining open points are in [provider integration details](docs/implementation/providers.md#provider-terms).

Two dot-matrix meters in the tab on the composer show context occupancy and the fullest limit window of the task's account. Their color moves from calm to amber to red as they fill. Hover for token counts, usage windows, reset estimates and report age. An account without limit windows, such as a Claude Enterprise seat, shows its usage credits instead: the share of the cap in the meters and in the sidebar, and the amount spent against the cap in the usage panel and in **Settings → Accounts**. Click either meter for the usage panel.

Kodem compacts a task's context when it reaches a share of the model's window. The default is 80%. **Settings → Providers → Context compaction** holds the rule for all providers, an optional rule for each provider and an optional rule for each model, each with a switch and a threshold from 30% to 95%. The provider's own CLI applies the threshold during a turn, and Kodem checks it again before each queued turn. **Compact now** in the usage panel, the `/compact` command and the command palette compact an idle task at once. A compaction shows as a working task with a "Compacting context" activity, can be stopped, and leaves a notice with the token counts. With the rule off, Codex may still compact when its window is almost full. They use data from the selected provider and account and remain unknown until it is available. Claude Code reports its five-hour and weekly windows and the session cost. Banked resets exist for Codex only. See [provider integration details](docs/implementation/providers.md) for protocol capabilities and validation limits.

Chat supports headings, bold and italic text, inline code, strikethrough, nested bullet and numbered lists, task lists, quotes, GitHub alert callouts, dividers, tables and syntax-colored code blocks. Text remains selectable. Web addresses are links even without link syntax; click a link to open it, and click a file reference to open it in the file browser. A run of tool calls has one line that counts what the agent did, totals its edits and shows the call that is running. The run is open while the agent works on it and lists its calls, one line each. It folds when the work moves on or the turn ends. A thought has a tray of its own between the runs: it shows its text while the agent thinks and folds to its first sentence afterwards. Runs and thoughts that follow one another without a reply between them have a parent line over all of them. It sums up what they did and folds the whole stretch into one line when the work moves on or the turn ends; open it to see its runs and thoughts, each foldable on its own. A run, a thought or a parent that you open or fold by hand keeps that state. A failed call stays visible while its run or its parent is folded. Open a call to see its command, status, duration and output. Edits from providers that report them show an inline diff. Thinking appears as a foldable row. Long output starts with a preview of up to 12 lines and expands inside a scrollable block. A copy control keeps access to the full call and output. When the agent reports a step list, a progress strip above the composer shows it. A column of ticks on the right edge of the conversation lists the messages you sent, with the turn in view marked. Point at a tick for a preview of the message and the start of its reply; click it to scroll there.

The Changes dropdown offers working-tree, staged, unstaged and task-baseline comparisons. Live comparisons refresh automatically while the Changes view or an open diff is visible. Selected diff text or lines retain their snapshot until **Load latest** is chosen; saved completion snapshots stay fixed. Selecting a file opens its diff above the composer by default; **Settings → Workspace → Open file diffs in** can use the right panel instead. The diff toolbar keeps only file identity, split/unified, refresh and close controls. Drag through code to select and copy text across lines. Drag the line numbers to select a range and add a comment below it. The resulting composer block retains the original snapshot, both old/new ranges, excerpt and comment even after files change.

Changes also include initialized submodules, nested Git checkouts, symlinked repositories and repositories referenced by local `file:` dependencies in Unity's `Packages/manifest.json`. Files are grouped by repository, and each diff shows its owning checkout path. Review feedback preserves that ownership. New tasks record a separate baseline for each linked repository. For repositories without a recorded baseline, Since task explicitly shows current uncommitted changes. Saved snapshots retain their original contents.

Paste copied files, folders or images with Command-V, drop them into the composer, or use the paperclip. Images show thumbnails; files show name and size. A folder is attached by reference: Kodem does not copy it, and the agent reads it in place. Click an image thumbnail in a draft, queued message or sent message to open a window-sized preview. The preview fits the whole image on opening and has icon-only zoom and close controls. Scroll to inspect an enlarged image, and press Escape to close it. File imports create stable private copies (up to 32 attachments, 32 MiB each file, 128 MiB total). Submitted messages retain their attachment and code-context blocks.

**Settings → Providers → Messages during a turn** selects Queue or Steer. Queue waits for successful completion; Steer adds input to the running turn without restarting it. The composer also exposes the current choice while work runs. A row of the composer, above the draft, shows upcoming messages and scrolls when there are many; expand an entry to inspect its content, cancel it, or restore it to an empty composer for editing. Failures and interruptions pause the queue until Resume. Unknown delivery requires Check history before resuming; uncertain messages are never replayed automatically.

**Settings → Notifications** controls alerts for tasks that need input or attention, finish, fail, or are interrupted. Choose Chime, Bell, Glass, Pulse, or Ascend, turn sounds off, and use **Test notification** to send a preview. Choosing a sound plays it, and **Play** plays the selected sound again without sending a notification. **Show while Kodem is active** shows the banner and plays the sound when Kodem is the frontmost app; when it is off, such alerts go to Notification Center only. The host sends alerts after task state changes, including while the window is closed. Repeated events and stored history do not replay alerts. Settings reports submission or permission errors; macOS notification and Focus settings control presentation.

The Files dialog provides read-only text previews. The terminal starts a shell in the task's checkout. Run check records the command, checkout revision, working-tree digest, output and exit code in the conversation. Skills & MCP shows provider-reported inventory and discovered instruction files.

## Current scope

The UI uses an integrated titlebar, an attention-first thread feed, a command palette, a docked composer with subtle spring motion, contextual review, tabbed preferences and a split file browser. Its visual language follows Liquid and is described in [dithered interface](docs/design/dithered-interface.md). It includes configurable sidebar widths, task search and sorting, pin/archive/rename actions, fourteen color themes, typeface, text size and interface scale settings, density, paged chat history, Markdown blocks, code highlighting, unified/split diffs, a foldable Changes tree, compact context headers, a feedback queue and a PTY terminal screen. Fonts are bundled.

This implementation supports local CLI providers. The broader [product specification](docs/design/product-spec.md) remains the roadmap. An agent can give work to a subagent on the other provider through Kodem's own `delegate_task` tool, a task can change its provider between turns, and `/fork` continues a task in a worktree of its own. A coding task saves its files after each turn and `/undo` restores them to before the last turn; choosing an earlier turn directly and restoring a provider conversation in place are not implemented. Native file editing, providers beyond Claude Code and Codex, PR delivery, MCP configuration editing, scheduling and remote access are not implemented. The Review workspace reads pull requests; it does not create, update or comment on them. Diff context expansion, intraline highlighting, partial staging, full terminal emulation controls and accessibility acceptance also remain open.

The earlier redesign was inspected using actual native GPUI Metal frames and app-local input events in an isolated project. Dark/light themes, narrow windows, file browsing, task creation, search, focus restoration, feedback and staging were exercised. This does not establish a complete accessibility or IME pass, or a real authenticated provider turn. The later conversation workflow changes were checked without visual testing or a real authenticated provider turn. See [implementation and validation](docs/implementation/progress.md) for the evidence and remaining gates.

| `kodem-host` | Task runtime ownership, delivery recovery, PTYs and check execution |
| `kodem-desktop` | Native GPUI-CE workspace and shared controls |

The host starts on demand. Closing the window keeps active tasks and terminals alive. Settings includes an explicit host shutdown action. An unused host with no active task, check or terminal exits after five minutes.

Nightly and Production data lives in `~/Library/Application Support/Kodem/` on macOS, `%LOCALAPPDATA%\Kodem\` on Windows and `~/.local/share/Kodem/` (or `$XDG_DATA_HOME/Kodem/`) on Linux. Debug uses `Kodem Debug` beside it with its own database, host socket, logs and window placement, so it can run alongside either release channel without upgrading their host. Debug starts with a separate workspace; existing data stays in the release directory. `KODEM_DATA_DIR` overrides the directory for any build. Database upgrades reject newer schemas, back up existing older schemas and apply changes transactionally. The data directory also holds `worktrees/` for task worktrees, `reviews/` for the detached worktrees of reviews and `chats/` for the scratch folders of chats.

`KODEM_CODEX_PATH` overrides the runtime path and must point into a complete Codex package meeting the minimum in `codex-min-version`. Otherwise Kodem selects the newest valid package from PATH, common installation locations and `~/.local/share/kodem/runtimes/*/` (`%LOCALAPPDATA%\kodem\runtimes\*\` on Windows). Selection happens at runtime, so upgrading Codex does not require rebuilding Kodem. The installer and application share the same minimum requirement. Future incompatible app-server protocol changes may still require adapter updates.

GPUI-CE 0.2.2 and its platform package 0.1.0 share one native type graph. The component layer contains a small, attributed port of GPUI Kit/base 0.6.0's Button and InputBase. It is not the full Kit library. See [third-party notices](assets/THIRD_PARTY.md).

The accepted [architecture](docs/design/architecture.md), [design guidance](docs/design/design-guidance.md), [implementation plan](docs/design/implementation-plan.md) and [research](docs/design/research.md) remain available. [Design validation](docs/design/validation.md) records the earlier dependency probe separately from this implementation.

The bundled app icon comes from `assets/app/AppIcon_1024x1024.png`. All build commands generate a complete macOS iconset from that source. Settings → Appearance offers fourteen themes as preview cards: Graphite and Paper, which are Kodem's own, and the classics Monokai, Dracula, One Dark, Nord, Tokyo Night, Gruvbox Dark and Light, Catppuccin Mocha and Latte, Solarized Dark and Light, and One Light. Code blocks, diffs and files take the code colors of the theme. The command palette switches themes too. Eighteen accent swatches follow; the first is the theme's own accent and the default, and the choice also colors controls, the text caret and selection, inline formatting and working indicators. The same page sets the typeface and size of interface text, the typeface and size of code, and the interface scale from 60% to 140%. The scale sizes spacing, controls and icons and leaves both text sizes alone; the title bar keeps the height of the macOS window controls.

Settings → Projects lets you rename projects and choose their accent and icon: one of 225 built-in glyphs, which you can search by name, or your own image. Imported images are stored as small PNG copies, so moving or deleting the original does not remove the project icon. New projects follow the app accent; existing saved project colors are retained. Removing a project hides it and its tasks while keeping files and local history. Reopen the repository to restore it. Active or unresolved work must finish before removal.

New Task opens an empty chat with an animated dot-matrix field and a greeting using the local account's first name. Click the project name to switch or add a repository, and choose New worktree or Current checkout inside the composer. Choose a model, reasoning effort and access before creating the task. The compact + button and Enter both create the task and immediately submit the first message. Working indicators use a 4×4 Bayer pulse. Buttons ripple from the press point, a new task flies from the composer to the thread feed, and a finished, failed or waiting task flashes on its row. Reduced motion shows static patterns everywhere and draws no effects.

The desktop retries failed local connections. An older idle host accepts an upgrade through its guarded shutdown request; active tasks and checks postpone that upgrade. A newer host is never downgraded by an older app. Settings distinguish an unavailable host from an unavailable runtime, and rejected operations are not replayed during reconnect.

By default the interface uses bundled Fira Sans for text and bundled IBM Plex Mono for code, buttons, metadata and uppercase labels. Inter for text and JetBrains Mono and Fira Code for code are bundled too. The font pickers also list the macOS system font, the typefaces that macOS ships, such as Helvetica Neue, Avenir Next, Menlo and Monaco, and common typefaces that you installed, such as IBM Plex Sans, Cascadia Code and Source Code Pro; these are not bundled. The title bar shows the Kodem mark and name in the mono typeface. The conversation lies on a field of a few wide, soft lights that rest at the sides and the bottom of the chat and drift slowly. A veil of the surface color lies over the reading column, so messages stay on a nearly plain surface. The field follows the open task: quiet and slow while idle, brighter and livelier in the accent while the agent works, breathing in amber while the task waits for you, green after a finished turn and red after a failure. The sidebar, the changes panel and the terminal slide open and closed. Task rows are flat two-line entries behind a large project tile, with dithered grain at the leading edge of the selected row and a moving dot field while their agent works.

Kodem uses HTTP streaming for its OpenAI sessions to avoid repeated WebSocket connection failures at thread startup. Retryable provider errors appear as transient reconnect status; terminal errors remain in the transcript. Custom provider selections are preserved.
